## Chapter 19.1 — Object Files, Symbols, and Relocations

### Interview & architecture questions

**1. Beyond machine code.** Sections (named byte ranges the linker merges), a symbol table (defined and undefined
names), and relocations (instructions for filling the holes), plus unwind tables and, optionally, debug information.
What survives into the running process: the contents of sections inside `LOAD` segments (`.text`, `.rodata`,
`.data`, `.eh_frame`, the GOT). Relocations survive only as *dynamic* relocations the loader applies at startup; after
that they're done. Symbol tables and debug information are never mapped.

**2. Three calls.** Same crate: `R_X86_64_PLT32` in the object file; the linker knows both addresses and writes a
direct `call rel32` (`call 15030 <local_helper>`). `std` (statically linked): rustc emits `R_X86_64_GOTPCREL`, so the
call reads a GOT slot; the linker keeps the indirection (no relaxation by default) and leaves an `R_X86_64_RELATIVE`
relocation for the slot, applied by the loader as load base + offset. `getpid`: also `GOTPCREL`, but the slot gets
`R_X86_64_GLOB_DAT getpid@GLIBC_2.2.5`, which the loader resolves by name and version in the loaded libraries at
startup (`BIND_NOW`). In the running process, the slot contains libc's address (listing `ch01-02`: `same as slot: true`).

**3. The GOT.** A table of address slots inside the executable (and each shared library). The linker creates it and
the dynamic loader fills it. With full RELRO (`BIND_NOW` plus a `GNU_RELRO` segment, the target default), every slot
is filled before `main` and the region is `mprotect`ed read-only; listing `ch01-02` finds the slot in an `r--p`
mapping. The reason: a writable table of code pointers is an attractive target for memory-corruption bugs, and there's
no need for it to stay writable once relocation is done.

**4. Relaxation.** A linker may rewrite `call *slot(%rip)` into a direct call when the target turns out to be in the
same output, if the relocation type permits it (`GOTPCRELX`/`REX_GOTPCRELX`). gcc emits those, so `helper` became
`addr32 call helper`. rustc 1.98.1 emits plain `GOTPCREL` for this target (relaxable relocations are off by default
[RUSTC]), so calls into `std` stay indirect. Listing `ch01-06` shows the unstable `-Z relax-elf-relocations=yes`
switching to `GOTPCRELX` and producing `addr32 call ... _print`.

**5. Allocator shims.** `__rust_alloc`, `__rust_dealloc`, `__rust_realloc`, and `__rust_alloc_zeroed` are generated by
rustc once, in the final binary (in a pseudo-crate `__rustc`), because the global allocator is chosen only when the
final artifact is linked. Every crate's allocations call them. With the default allocator, `__rust_alloc` is a single
`jmp __rdl_alloc` (`std`'s `System` allocator, which calls `malloc`). With `#[global_allocator]`, it calls your
`GlobalAlloc::alloc` (listing `ch01-04`).

**6. "Stripping makes us faster."** False for run time: symbol tables and debug information aren't mapped, so the
running program doesn't touch them. True-ish for deployment: smaller files pull and copy faster. The cost is
diagnosability: without symbols, backtraces are addresses (`<unknown>`), so you need a separate debug file matched by
build-id.

**7. Build-id.** A hash the linker computes over the output and stores in a note section (`readelf -n` shows it). It
identifies *this exact binary*; symbol servers and debuggers use it to match debug files. It changes whenever any
output byte changes, including paths recorded in debug information: listing `ch01-05` built the same source in two
directories and got different build-ids with `-g`, identical ones without `-g` or with `--remap-path-prefix`.

**8. ELF vs JVM resolution.** ELF resolves at link time and, with `BIND_NOW`, the rest at process start, so a missing
symbol or version is an error before `main` (Chapter 19.2's `version 'GLIBC_2.99' not found`). The JVM resolves
constant-pool entries lazily at the first execution of each site, so a missing class or method is a
`NoClassDefFoundError`/`NoSuchMethodError` minutes into a run. ELF lazy binding (`-z lazy`) moves some ELF failures to
first call too, which is one reason full RELRO is the default.

### Debugging exercise (duplicate `hash_bytes`)

1. Whether there's an error depends on how each definition enters the link. Two definitions in object files given
   directly to the linker: duplicate-symbol error. A definition inside a static archive (`.a`): the linker pulls an
   archive member only to resolve a still-undefined symbol, so if your crate's object already defines `hash_bytes`,
   the C library's member may never be pulled, and the library's other members silently call *your* function. A
   shared library compiled with default visibility: the executable's definition **interposes** on the library's own
   internal calls (they go through the library's GOT, Chapter 19.2). In all the silent cases, the C code calls a
   function with a different contract and gets wrong results. A release-only symptom points at a link that differs
   between profiles (LTO, a different link order, a static archive in release versus a shared library in development).
2. `nm -C` on the final binary shows one `T hash_bytes` and whose it is; `objdump -d` on the library's call sites
   shows where they go; for shared libraries, `LD_DEBUG=bindings` prints each binding the loader makes; a linker map
   file (`-C link-arg=-Wl,-Map=out.map`) shows which archive members were pulled and why.
3. Rust side: never export generic names; prefix (`meridian_plugin_hash_bytes`) or use `#[export_name]` with a prefix.
   C side: make library-internal functions `static` or build with `-fvisibility=hidden`. Choose the Rust-side rename
   (you control it and it fixes this instance today), and ask the vendor for hidden visibility (it fixes the class).

### Selected exercises

- **Beginner (logstat's symbols).** Expect far fewer `logstat` functions than in the source: release builds inline
  small functions into callers, and generic instances appear under `logstat`'s name only where they were instantiated
  (Chapter 7.1). The missing functions are inlined, not absent.
- **Advanced (relaxation measurement).** Predicted: a difference within noise for most code, because the GOT load hits
  the cache and the indirect branch is predicted after the first call. It can matter for very small, non-inlined
  cross-crate functions in tight loops. Report the result with its spread; the lesson is to measure before asking for
  an unstable flag.
- **Architecture (symbol policy).** Internal service: `line-tables-only`, strip debug info from shipped binaries, keep
  symbols, upload debug files by build-id, retain for the longest deployment lifetime plus a margin. On-prem agent:
  strip everything shipped (disclosure), keep debug files internally, map crash reports by build-id. FFM library:
  keep its dynamic symbols minimal (only the exported C API), strip the rest, upload debug files; the JVM's crash
  files (`hs_err_pid*.log`) record native frames by address, which you symbolize offline.

## Chapter 19.2 — Static and Dynamic Linking

### Interview & architecture questions

**1. What's static and what's dynamic.** All Rust code (your crates, dependencies, `std`, `core`) is linked
statically from `.rlib`s. glibc (`libc.so.6`), the unwinder (`libgcc_s.so.1`), and the loader are dynamic. Rust code
is static because Rust has no stable ABI: a shared `libstd` works only with the exact compiler build that produced it
(`libstd-64f5f36fb0927694.so`). glibc is the platform's C ABI, stable and versioned.

**2. The oldest glibc.** The binary's newest *mandatory* version need for `libc.so.6` (`readelf -V`). Weak references
don't lower it, because the version need itself is recorded without the `WEAK` flag (`Flags: none` for `GLIBC_2.39` in
listing `ch02-01`, with both rust-lld and GNU ld in a scratch comparison), and the loader checks version needs before
anything runs. Independently, any program linked against glibc ≥ 2.34 needs `__libc_start_main@GLIBC_2.34` from the
start files.

**3. `error while loading shared libraries`.** The dynamic loader failed before any of your code ran: it couldn't find
`libfee.so` in any search location. The process exits with status 127, the same status a shell uses for "command not
found", so check stderr to tell them apart.

**4. Interposition.** The loader resolves each dynamic symbol by searching loaded objects in order: the executable,
then `LD_PRELOAD` libraries, then `NEEDED` libraries in load order; the first definition wins. `libfake.so` defined
`getpid`, so the dynamic binary's GOT slot got the fake function and `std::process::id()` returned 4242. The static
binary resolved `getpid` at link time into its own copy of glibc's code; there's no lookup for a preload to win.

**5. `cdylib` exports.** Only `#[no_mangle]` (or `#[export_name]`) items are in the dynamic symbol table; listing
`ch02-03` shows one defined dynamic symbol, `risk_score`. `pub` is Rust-level visibility between crates; it doesn't
make a function part of the shared library's ABI.

**6. Static glibc vs musl.** glibc's name resolution (NSS), `iconv`, and anything using `dlopen` load shared glibc
components at run time, which must match the glibc the program was built with, so a "static" glibc binary still
depends on the host's glibc for those features. musl is designed for static linking: its resolver and locale handling
are compiled in. The musl trade-offs are a slower `malloc` under multithreaded load (replace it: mimalloc/jemalloc) and
behavioral differences in DNS resolution.

**7. Proc macros.** A proc-macro crate is compiled into a shared library for the *host*, exporting a table of macros
(`__rustc_proc_macro_decls_<hash>__`). The compiler `dlopen`s it during expansion (listing `ch02-04`'s `LD_DEBUG`
trace) and runs its code with your build's privileges. Implications: proc macros can do anything on the build machine
(review and allowlist them, Part XXII), and when cross-compiling they're still built for the host.

**8. `--release` vs the glibc floor.** `javac --release 17` makes the compiler reject newer APIs, so the output runs
on every Java 17 runtime by construction. Nothing tells rustc or the linker which glibc the fleet has; the floor is
whatever the build machine's glibc makes it. You get the Java property only by building on the oldest supported glibc
(or with a toolchain that targets an older glibc explicitly), or by shipping musl.

### Debugging exercise (`LD_LIBRARY_PATH` from a sidecar's template)

1. Every dynamically linked process's loader reads `LD_LIBRARY_PATH` from its *own* environment, and the pod's
   environment template gave it to every container. `LD_LIBRARY_PATH` is searched before `RUNPATH` and the system
   directories, so the loader found `/opt/vendor/lib/libgcc_s.so.1` first. Only production's `/opt/vendor/lib` held
   that file.
2. `LD_DEBUG=libs` would show `trying file=/opt/vendor/lib/libgcc_s.so.1` succeeding, then the version check failing,
   with an error like `version 'GCC_4.2.0' not found (required by ./svc)` (the binary needs `GCC_3.0`, `GCC_3.3`, and
   `GCC_4.2.0` from `libgcc_s.so.1`, per this Part's `readelf -V` output). A found-but-too-old library exits with
   status 1, as in listing `ch02-01`; a missing library would be 127.
3. Manifest: scope `LD_LIBRARY_PATH` to the sidecar container only (and question why the sidecar needs it). Build:
   ship the service as a static musl binary, which has no dynamic loader and is immune to the whole class. A
   `RUNPATH` doesn't help, because `LD_LIBRARY_PATH` takes precedence over it.

### Selected exercises

- **Intermediate (two `libfee.so`s).** `LD_LIBRARY_PATH` wins over `RUNPATH`, so the renamed library is loaded; the
  loader then can't resolve `fee_bps` and fails with `undefined symbol: fee_bps` (with `BIND_NOW`, at startup).
- **Systems (sharing).** On a desktop or build host, PSS for `libc.so.6` is a small fraction of its RSS per process,
  because dozens of processes share it. On a node running 30 copies of one static service, the static binary's code
  pages are shared among those 30 copies anyway (same file, page cache), so dynamic linking saves little there.
- **Architecture (three environments).** Kubernetes: musl static or glibc with a pinned oldest-glibc builder,
  distroless or scratch images, libc CVEs handled by rebuild pipelines. Customer VMs: musl static (you can't control
  their glibc), patching by releasing new versions. Lambda: static binaries (musl, or glibc matched to the runtime's
  Amazon Linux version), size and cold start matter (Chapter 19.4).

## Chapter 19.3 — Executable Formats: ELF, PE, Mach-O

### Interview & architecture questions

**1. Segments vs sections.** Segments (program headers) describe what to map where, with which permissions: the
loader's and kernel's view. Sections describe named pieces for the linker and tools. The kernel uses only program
headers; section headers can be removed entirely and the program still runs.

**2. `memsz`, `filesz`, RELRO.** `memsz > filesz` means zero-initialized memory (`.bss`, `.tbss`) that occupies no file
space; the loader maps zeroed pages for the difference. The first writable `LOAD` segment coincides with `GNU_RELRO`
because it holds data that relocation writes (`.data.rel.ro`, `.got`, `.dynamic`): writable during relocation, then
`mprotect`ed read-only.

**3. CIE, FDE, personality, LSDA.** An FDE describes how to unwind one function's frames (find the return address and
saved registers at any instruction); a CIE holds rules shared by many FDEs, including which **personality routine** to
call; the **LSDA** is per-function language data (call-site table: which landing pad covers which call). A panic calls
the unwinder, which for each frame finds the FDE (through `.eh_frame_hdr`'s search table), reads the CIE, and calls the
personality routine (`rust_eh_personality`) with the LSDA. Phase 1 searches for a handler (`catch_unwind`); phase 2
walks again and runs landing pads (drops), each ending in `_Unwind_Resume`.

**4. Landing pads.** Since 1.81 an `extern "C"` function can't unwind (an unwind reaching the boundary aborts), so a call
to one can only return normally, and there's nothing for a landing pad to do. With `extern "C-unwind"` under
`panic=abort`, a foreign exception can still arrive through the call, so the compiler emits a pad that drops the guard
and calls `panic_cannot_unwind`, which aborts.

**5. `debuginfo=0` and 4.5 MB.** The debug sections come from the precompiled standard library, which ships with line
tables. `-C strip=debuginfo` (or `strip --strip-debug`) removes them: 462 KB in listing `ch03-03`.

**6. Frame pointers vs unwind tables.** Frame pointers cost two instructions per non-leaf function and one register
(listing `ch03-05`: +6 bytes); sampling profilers use the `rbp` chain for cheap stack walks. Unwind tables cost file
size, not steady-state memory (pages are faulted in only when used), and are needed by the unwinder (panics), backtraces,
debuggers, and DWARF-based profilers. They're complements, not alternatives.

**7. PE and Mach-O debug information.** Windows puts debug information in a separate PDB file by design, matched to the
binary by a GUID and age; macOS collects it in a separate `.dSYM` bundle matched by the binary's UUID. ELF can keep it
in the file or split it (`.dwo`/`.dwp`, or `objcopy` + debuglink) and matches by build-id. A crash pipeline must record
each platform's identifier at build time and upload the matching artifact; one scheme doesn't cover all three.

**8. Java's tables.** The `Code` attribute's `exception_table` maps bytecode ranges to handlers, like the LSDA's call-site
records; both implement zero-cost exceptions (no work on the happy path). `LineNumberTable` maps bytecode offsets to
lines, like DWARF's line tables, and is kept by default, which is why Java stack traces always have line numbers.

### Debugging exercise (C++ exception through a `panic=abort` build)

1. Build C's pad shows what happens: the exception reaches the Rust frame, the pad runs the guard's drop glue, and
   then calls `panic_cannot_unwind`, which aborts. Under `panic=abort`, unwinding through Rust frames isn't supported,
   and a foreign exception arriving through a `C-unwind` call aborts the process by design.
2. With `panic=unwind` (build B), the pad runs the drop and calls `_Unwind_Resume`, so the exception continues to the
   C++ handler further up, as the team expected. With `extern "C"` declarations, an unwind can't cross the boundary
   at all: the process aborts at the boundary (Chapter 8.3).
3. Catch C++ exceptions in C++, at the boundary: wrap the C++ API in `noexcept` functions that translate exceptions
   into error codes, declare them `extern "C"`, and turn the codes into `Result`s on the Rust side. Reserve `C-unwind`
   for designs that really need exceptions to cross, and then use `panic=unwind` and test the path.

### Selected exercises

- **Advanced (two guards, a nested call).** Predicted: one call-site record per call that may unwind, each pointing at
  a pad that drops exactly the guards alive at that call, in reverse order of creation. Verify with the section dump.
- **Systems (frame pointers).** Expect small effects on most code (predicted from mechanism: one fewer register) and
  larger effects on register-hungry kernels with many live values. Report with best-of-N and spread.

## Chapter 19.4 — From Executable to Process

### Interview & architecture questions

**1. Before `main`.** Kernel: `execve` reads headers, maps segments, maps the loader and the vDSO, builds the stack
(argc, argv, envp, auxv), jumps to the loader. Loader: relocates itself, reads `ld.so.cache`, opens and maps each
`NEEDED` library, applies relocations, sets up TLS, `mprotect`s RELRO ranges, runs initializers, jumps to `_start`.
glibc: `_start` aligns the stack and calls `__libc_start_main`, which initializes libc and calls `main`. `std`: the
generated `main` calls `lang_start`, which checks fds 0–2, ignores SIGPIPE, finds the main thread's stack, installs the
stack-overflow handler on an alternate stack, and calls your `main` inside `catch_unwind`.

**2. The auxiliary vector.** Key/value pairs the kernel puts on the initial stack after `envp`. `AT_PHDR`/`AT_PHNUM`
tell the loader where the program headers are; `AT_ENTRY` where to jump when it's done; `AT_BASE` where the loader
itself is; `AT_SYSINFO_EHDR` where the vDSO is (glibc uses it for fast `clock_gettime`); `AT_RANDOM` gives 16 random
bytes for stack-protector canaries and pointer mangling; `AT_SECURE` tells the loader to ignore `LD_*` variables for
setuid programs.

**3. `catch_unwind` around `main`.** So that a panic escaping your `main` is turned into a clean exit with status 101
after the panic hook runs, instead of unwinding into glibc's C frames (`__libc_start_main`), which can't be unwound
through; without it, such a panic would abort (status 134). The outer `catch_unwind` protects the runtime's own setup
and teardown the same way.

**4. SIGPIPE.** `std` sets SIGPIPE to "ignore", so a write to a closed pipe or socket returns `EPIPE`
(`ErrorKind::BrokenPipe`) instead of killing the process. Right for servers: a client disconnecting mid-response
mustn't kill the service. Surprising for CLIs: in `prog | head`, `println!` panics with a "Broken pipe" error when
`head` exits (exit 101 and a message), where a C tool would die silently. Handle `BrokenPipe` explicitly (Project L1),
or use the unstable `-Zon-broken-pipe=kill` option [VERSION].

**5. Stack overflow.** Every thread has a `PROT_NONE` guard page below its stack. An overflow faults on it, the kernel
delivers `SIGSEGV`, and `std`'s handler, running on the alternate signal stack because the normal one is exhausted,
checks that the faulting address is in a guard page, prints "has overflowed its stack", and calls `abort`. Hence
`SIGABRT` (134), not `SIGSEGV` (139).

**6. Raw statuses.** `0x300`: exited with code 3. `0x6500`: exited with code 101 (a panic in `main`). `0x86`: killed by
signal 6 (`SIGABRT`), with the core-dump bit (`0x80`) set; a shell shows 134. `0x9`: killed by signal 9 (`SIGKILL`), no
core; a shell shows 137.

**7. ASLR in the container.** Disabling randomization for a process uses `personality(ADDR_NO_RANDOMIZE)`, and the
container's seccomp filter doesn't allow it ("Operation not permitted"). Production containers commonly restrict
debugging and introspection system calls, so plan diagnostics that don't depend on them: core dumps collected by the
node, symbolization offline by build-id, debug sidecars where policy allows.

**8. JVM vs Rust startup.** Both go through the kernel and the dynamic loader. The JVM then initializes a runtime (heap
reservation, GC and JIT threads, class loading and verification) before `main`; Rust's `std` does a handful of system
calls. Java's options are AppCDS, CRaC, and Native Image; Rust's are static linking, a clean environment, and not
starting processes needlessly.

### Debugging exercise (exit 134, no message)

1. 134 is `SIGABRT`: `process::abort`, a panic under `panic = "abort"`, a double panic, or a stack overflow. The
   256 KiB worker stacks plus a recursive-descent parser over partner JSON make a stack overflow the best fit.
2. `std` writes the message to stderr from the signal handler, and nothing else runs afterwards. If the log pipeline
   collects only structured logs (for example, a JSON logger on stdout) or drops the last lines of a dying container,
   the message is lost. `kubectl logs --previous` shows the previous container's raw stderr and is the first place to
   look.
3. Confirm with `kubectl logs --previous`, core dumps (the faulting address in the guard page), and replaying the
   partner payloads offline with the same stack size. Fix: restore a sane stack size (or size it from measurement,
   Chapter 11.1), add a depth limit to the parser (the Part IX interlude's 64-level limit), or make the parser
   iterative; `serde_json` enforces a recursion limit of 128 by default.

### Selected exercises

- **Beginner (`panic = "abort"`).** The `error` row becomes `SIGABRT`: raw `0x86`, `signal() = Some(6)`, shell 134,
  and no unwinding happens (no destructors run).
- **Advanced (`#![no_main]`).** The `poll`, SIGPIPE, `/proc/self/maps`, and `sigaltstack` calls disappear. A stack
  overflow becomes a plain `SIGSEGV` (139) with no message, and a write to a closed pipe kills the process with
  `SIGPIPE`.

## Chapter 19.5 — Virtual Memory, Pages, and mmap

### Interview & architecture questions

**1. `VmSize`, RSS, PSS.** `VmSize` is all mapped address space (reservations included). RSS is resident pages,
counting shared pages fully in every process. PSS divides shared pages among their users. For capacity planning, use
PSS (or the cgroup's own accounting for containers), measured at peak, never `VmSize`.

**2. Minor faults.** The first access to a page that's mapped but not present: the kernel allocates a frame (zeroed for
anonymous memory, or from the page cache for files) and installs it, without disk I/O. 64 MiB is 16,384 pages, so
16,384 faults; the second pass found every page present.

**3. `MADV_DONTNEED`.** For private anonymous memory, it discards the pages: the mapping stays, but the contents are
gone, and the next access gets a fresh zero-filled page. Hence value 0.

**4. Freed but resident.** Small blocks live in the heap; freeing puts them on malloc's free lists, and glibc returns
memory to the OS automatically only from the top of the heap. `malloc_trim(0)` also releases whole free pages in the
middle, which is why RSS fell to 2.2 MiB. With every 64th block alive, nearly every 4 KiB page (about 50 chunks each)
still holds a live chunk, so there are almost no whole free pages to release.

**5. `mmap` won.** No copy and no new allocation: faults just map page-cache pages that are already there, 16 at a
time with fault-around (672 faults for 10,730 pages). `RssFile` means those pages are page cache: they count toward
the container's memory usage but are reclaimable under pressure, unlike anonymous memory.

**6. `SIGBUS`.** Touching a mapped page that no longer has file data behind it (the file shrank) raises `SIGBUS`, which
kills the process. `Mmap::map` is `unsafe` because Rust would hand you a `&[u8]` whose validity and immutability depend
on other processes, which the compiler can't check; the caller must guarantee it.

**7. Canonical addresses.** With 4-level paging, x86-64 translates 48 bits and requires bits 48–63 to equal bit 47;
user space is below 2^47. Pointer tags must live in bits the hardware ignores or be stripped before use. Arm's TBI
ignores the top byte; Intel's LAM masks configurable upper bits, so tagged pointers can be dereferenced directly.

**8. Rust vs Java.** Rust: `Mmap` is unmapped deterministically on drop, `SIGBUS` is fatal, and memory return depends
on the allocator (`munmap` for large blocks, `malloc_trim`, or a decaying allocator). Java: `MappedByteBuffer` is
unmapped only when collected (deterministic with FFM `Arena`), `SIGBUS` becomes an `InternalError`, and heap memory
return depends on the collector (G1 and ZGC can uncommit).

### Debugging exercise (9.4 GB `VmSize`)

1. Per thread: a 2 MiB stack plus guard page, a small alternate signal stack with its own guard page, and, for threads
   that allocate, a glibc arena reservation of 64 MiB (glibc limits the number of arenas to 8 per core by default
   [LIB]). 128 threads × about 66 MB ≈ 8.4 GB, plus the heap and libraries.
2. Almost nothing for RSS: those reservations are address space. The OOM risk is set by resident memory (and allocator
   retention across arenas), not by `VmSize`. Fewer arenas can reduce retained memory somewhat at the cost of more
   allocator contention.
3. `MALLOC_ARENA_MAX` (the `glibc.malloc.arena_max` tunable). Decide by measuring peak RSS and allocator contention
   with the setting at, say, 2, 4, and the default, under production-like load.

### Selected exercises

- **Intermediate (fault cost).** Expect about 2 µs per first-touch fault on the Playground (Chapter 20.4 measured it);
  divide the first pass's time by 16,384 and compare with the second pass's time for the same loop, which pays no
  faults.
- **Advanced (arena instead of boxes).** Dropping a bump arena frees its few large chunks at once, and large chunks are
  `munmap`ed, so RSS returns immediately. Candidates at Meridian: per-request parse trees, per-batch settlement
  records, anything with a clear lifetime boundary.

## Chapter 19.6 — Syscalls, File Descriptors, Processes, and Threads

### Interview & architecture questions

**1. `File::open`.** `std` converts the path to a NUL-terminated C string (rejecting interior NULs), adds `O_CLOEXEC`,
and calls libc's `open`; libc executes the `syscall` instruction with `rax = openat`, arguments in registers, and
converts a negative result into `-1` plus `errno`; the kernel (after seccomp in a container) looks up the path and
installs the lowest free descriptor. `std` wraps the result in `File` (closed on drop) or converts `errno` into an
`io::Error`.

**2. 540 ns vs 24.5 ns.** `getpid` enters the kernel: privilege switch, entry code, mitigations, the container's seccomp
filter, return. `clock_gettime` is served by the vDSO: kernel-provided code mapped into the process that reads
kernel-maintained time data from `[vvar]`, so no kernel entry at all.

**3. `O_CLOEXEC`.** The descriptor is closed automatically in any `execve`. Setting it atomically at `open` matters
because another thread might spawn a child between an `open` and a later `fcntl`. Without it, children inherit the
descriptor (listing `ch06-02`: the child saw fd 5).

**4. Copy-on-write and threads.** `fork` copies page tables and marks private pages read-only in both processes; the
first write to a page copies it (4,097 faults for 4,096 pages written; reading caused none). In a multithreaded program
only the forking thread exists in the child, so locks held by other threads at that moment (inside `malloc`, a logger)
stay locked forever in the child.

**5. `clone(0x4111)`.** `CLONE_VM | CLONE_VFORK | SIGCHLD`: the child shares the parent's memory and runs on a small
separate stack until it calls `execve`, while the parent is suspended. No page tables are copied, and because the
child only execs, the locking problem of `fork` doesn't arise. This is glibc's `posix_spawn`, which `Command` uses when
it can.

**6. A thread.** `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS |
CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID`. `CHILD_CLEARTID` makes the kernel clear the thread's TID word and wake
futex waiters on it when the thread exits; `join` waits on that futex (the `futex(op=9)` in the trace).

**7. `Mutex` and the kernel.** Only under contention: `FUTEX_WAIT` when the lock stays taken after a short spin, and
`FUTEX_WAKE` on unlock only if a waiter exists. 10,000 uncontended lock/unlock pairs made none. Half a million `futex`
calls per second means heavy contention (threads repeatedly sleeping and waking on some lock): find the lock with an
off-CPU profile and reduce sharing (Chapter 11.7).

**8. Descriptor leaks.** Rust closes a descriptor when its owner is dropped, deterministically, so a leak is a value you
kept, `mem::forget`, or inheritance into a child. In Java, an unclosed stream is closed eventually by a cleaner after
garbage collection, so leaks look like "too many open files until the next GC".

### Debugging exercise (EMFILE spin)

1. `accept` needs a new descriptor and there are none, so it fails with `EMFILE`; the pending connection stays in the
   listen queue, so the listener stays readable and the next `accept` fails immediately again: a tight loop.
2. One core spins in the loop and the log, no new connections complete, existing work gets less CPU, and clients
   retry, adding pressure: a metastable overload.
3. In the loop: on `ErrorKind::TooManyOpenFiles`, pause accepting (sleep a few milliseconds or deregister the
   listener from the event loop), log at most once per second, and consider closing idle connections; some servers
   keep one reserve descriptor to accept-and-close excess connections gracefully. Prevention: a connection limit well
   below the descriptor limit, the soft limit raised to the hard limit at startup, and an alert on descriptor usage
   (§9).

### Selected exercises

- **Beginner (descriptor numbers).** New descriptors take the lowest free numbers, so the 10 new sockets reuse the
  numbers freed by closing every other one, in increasing order.
- **Advanced (spawn costs).** Expect thread spawn + join in the tens of microseconds and `Command::status()` for
  `/bin/true` around a millisecond (the child's own startup, Chapter 19.4, dominates). Explain with the traces: the
  thread path makes a handful of system calls; the process path adds the child's whole startup.

## Part XIX Review — Capstone: the release audit

### Part A: predictions from the diff

- `target-cpu=native`: code built for the CI runner's CPU (AVX2/AVX-512); `SIGILL` on older hosts when those paths
  run (Chapter 2.1's incident). Harmful.
- `relocation-model=static`: a non-PIE executable, so the executable's own addresses aren't randomized; on x86-64 the
  performance claim is folklore (RIP-relative addressing makes PIC nearly free). Harmful for the security review.
- `-z lazy`: removes `BIND_NOW`, so RELRO is partial and the GOT stays writable after startup; startup gains are
  negligible. Harmful.
- `-z execstack`: makes the stack executable, disabling a basic protection. Copied from an unrelated build. Harmful.
- Absolute `rpath` to a CI directory: the loader will search a path that doesn't exist on the VMs (or, worse, exists
  and is writable by someone), and it leaks build-system layout. Harmful hygiene.
- `debug = 2` shipped inside the binary: 4.5 MB instead of about 0.5 MB, source paths and internals shipped, and no
  separate debug file for the crash pipeline. Harmful as configured.
- `pidfd_open` via the glibc wrapper: glibc 2.36, newer than the VMs' 2.35: the binary won't start.

Ranking by blast radius: the glibc floor (nothing starts on any VM) > `target-cpu=native` (crashes on a subset of
hosts, minutes after start, hard to diagnose) > the hardening regressions (PIE, RELRO, NX: a failed PCI review and
more exploitable memory bugs) > the `rpath` > the debug-info configuration (size and disclosure, fixable in the
pipeline).

## Interview mode

1. Same crate: a `PLT32` relocation becomes a direct call. `std`: a `GOTPCREL` call through a GOT slot that the loader
   fills with a `RELATIVE` relocation (no relaxation by default in rustc). `libc.so.6`: a GOT slot filled by name and
   version (`GLOB_DAT`) at startup.
2. No stable Rust ABI, so Rust code must be compiled together (statically); glibc is the stable, versioned platform ABI
   and brings NSS and other shared components.
3. A version need records "this binary requires version node `GLIBC_2.x` of `libc.so.6`". The loader checks all
   mandatory needs before running anything. Linking on a newer glibc can add needs you didn't ask for: the start
   files' `__libc_start_main@GLIBC_2.34`, and `std`'s weak references, whose needs are still mandatory.
4. `strip=debuginfo` removes DWARF (no file:line) but keeps symbols (function names in backtraces and profilers);
   `strip=symbols` removes names too (addresses only). Both lose nothing at run time; both require a separate debug
   file to recover what was removed.
5. The kernel maps segments, the loader and the vDSO, and builds the stack; the loader maps libraries, relocates, and
   applies RELRO; `_start` aligns the stack and calls `__libc_start_main`; `lang_start` checks stdio fds, ignores
   SIGPIPE, installs the stack-overflow handler, and calls `main` inside `catch_unwind`.
6. Panic: 101 (`lang_start` turns it into an exit code). Stack overflow: 134, because `std`'s guard-page handler
   aborts. OOM kill: 137, `SIGKILL` from the kernel, and nothing in the process runs.
7. SIGPIPE is ignored, so writes to closed pipes return `BrokenPipe` errors. A CLI in `| head` must handle that error
   (or `println!` will panic), where a C tool would be killed silently.
8. A thread's 2 MiB stack is added to `VmSize` at spawn, but only the touched pages (16 KiB when idle, +1,024 KiB after
   entering a 1 MiB frame in listing `ch05-02`) are in RSS.
9. Freed small blocks stay in the allocator's free lists; glibc returns only the top of the heap automatically.
   `malloc_trim` releases whole free pages elsewhere, unless fragmentation leaves a live block on nearly every page.
10. Use `mmap` for large files the process owns that nobody modifies (immutable segments), for random access and
    zero-copy. Refuse it for files other processes may truncate or rewrite (logs, uploads): `SIGBUS` can't be handled
    as an error.
11. Hundreds of nanoseconds here (540 ns, container with seccomp); the vDSO maps kernel code and data into the process,
    so `clock_gettime` (and therefore `Instant::now()`) runs in user space in about 25 ns.
12. `fork` copies page tables and is unsafe in multithreaded processes (locks held by vanished threads). `Command` uses
    `posix_spawn`: `clone(CLONE_VM | CLONE_VFORK)`, sharing memory until `execve`.
13. Only when it's contended: a thread that can't get the lock after spinning sleeps with `FUTEX_WAIT`, and unlocking
    wakes a sleeper with `FUTEX_WAKE`. Uncontended locking is pure user-space atomics.
14. `line-tables-only` builds, reproducible paths (`--remap-path-prefix`), debug files extracted and uploaded by
    build-id as a release-gate step, binaries shipped with symbols but without debug information (or fully stripped
    for software shipped to customers), retention for the life of every deployed build, and offline symbolization in
    the crash pipeline.
15. (a) musl static or glibc built on the fleet's oldest glibc, on minimal images. (b) musl static: runs on any
    customer Linux, no glibc floor. (c) A `cdylib` built on the oldest glibc of the JVM hosts, with a minimal exported
    symbol set, `extern "C"` entry points that catch panics, and debug files kept by build-id.
